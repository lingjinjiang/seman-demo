# 智能问数 Agent —— Harness 选型对比说明

> 面向 P3（LLM 问数 Agent）的选型文档。结论先行，后面是依据。
> 相关设计：`design-ouline.md` §1.5（发布边界）、§6（执行/生态接口）；`roadmap.md` P3。

---

## 0. 结论摘要

1. **本项目的 harness 很薄，选型不是重点，边界才是重点**。架构已经定了「LLM 只产出语义查询 IR、
   编译器是 Rust 纯函数、消费只读已发布版本」，所以 harness 只需负责**工具循环 + 结构化输出 +
   失败回灌 + trace**，不需要它理解 SQL。
2. **DeepSeek Harness（DSH）架构契合度最高，但成熟度是硬伤**（2026-08 创建、developer preview、
   官方明示会有破坏性变更；Node 运行时栈）。详见 §4.9。
   **建议：不作为 P3 第一版的默认依赖，但列为并行评估的首选候选**——它的插件模型、
   append-only 会话日志、guarded tool pipeline 几乎就是照着我们这几条约束长的。
3. **第一版首选在 Pydantic AI 与 OpenAI Agents SDK 之间二选一**：
   - 更看重「输出即契约、校验失败即重试」→ **Pydantic AI**；
   - 更看重「依赖最轻、工具循环与 tracing 开箱」→ **OpenAI Agents SDK**。
4. **流程一旦出现多步审批 / 长事务 / 断点续跑，再上 LangGraph**；不要在只有一条主链路时就上状态机。
5. **DSPy 不是 harness，是优化器**：用 20 题评测集把 NL→IR 的准确率刷上去，属于第二阶段的增益项，
   不建议在第一版就引入。
6. **不建议**：CrewAI / AutoGen 这类多智能体角色扮演（本任务不需要多智能体，只会引入不确定性）；
   也不建议把 Dify / Coze / n8n 这类低代码平台放进核心问数链路（契约校验、私有化、
   「只读已发布版本」的纪律都对不齐），它们更适合做内部原型。
7. **一个被低估的选项是自研薄循环**：给定上面这条链路，约 200 行 Python（SDK + JSON Schema 校验 +
   重试上限）就能覆盖 90% 需求，且没有任何框架升级风险。是否引框架，取决于你要不要它自带的
   trace / eval / 人工介入能力。

## 1. Harness 在这套架构里到底负责什么

职责边界（来自 `design-ouline.md` §6 与 roadmap P3）：

```
用户提问
   │
   ▼
[Agent 服务 (Python)]  ← harness 负责这一层
   │  1. grounding 检索：命中 metric / dataset / field / ontology 事实
   │  2. 生成语义查询 IR（结构化输出，JSON Schema 约束）
   │  3. 调工具：compile / validate / execute
   │  4. 失败回灌重试（≤N 次）；歧义则反问，不硬猜
   │  5. 回答附"依据"（命中的 artifact，可展开 SQL）
   │
   ├──REST──▶ [Rust 后端]
   │             ├─ query.rs    IR → SQL（纯函数，方言后端）
   │             ├─ existence.rs 列引用 × schema 快照校验
   │             └─ 只读「已发布版本」快照（/released）
   ▼
执行（Trino / PG）+ 结果解释
```

**硬约束（选型必须服从，不可妥协）**：

| # | 约束 | 对 harness 的要求 |
|---|------|-------------------|
| C1 | LLM 永不直出 SQL | harness 必须能强制结构化输出，而不是自由文本 |
| C2 | 编译器是 Rust 纯函数 | harness 只做编排，**不得把编译/校验逻辑复制到 Python** |
| C3 | 消费方只读已发布版本 | harness 的检索与编译输入都指向 release 快照，不能读工作区 |
| C4 | 重试有上限、行列有硬限 | harness 必须支持显式步数/次数控制与终止条件 |
| C5 | 私有化部署 | 不依赖任何 SaaS 控制面；模型走可替换的 provider |
| C6 | 可评测（20 题标准集） | harness 需可重放、可记录每步输入输出 |

## 2. 评估维度

按本项目权重排序（1 最重要）：

1. **结构化输出的契约强度**：能否直接绑定 JSON Schema / 类型模型，失败时能否拿到结构化错误。
2. **工具循环可控性**：步数、重试、终止条件、确定性；是否能「诊断回灌」。
3. **可观测与评测**：trace、重放、与评测集对接的难易。
4. **检索（grounding）集成**：与 Rust 侧 FTS / 向量检索拼装的顺手程度。
5. **依赖面与私有化**：依赖体积、许可证、是否必须联网。
6. **进程边界契合**：Python 薄服务 + REST 调 Rust 的形态是否自然。
7. **人工介入**：歧义反问、结果确认、审批。
8. **维护成本与生态**：迭代速度、文档质量、社区活跃度。

## 4. 逐项分析

### 4.1 Pydantic AI —— 契约优先，最贴合「IR 即输出」

- **命中 C1/C2/C4**：原生以 Pydantic 模型作为输出契约，校验失败会给出结构化错误，天然适合把
  「生成 IR → schema 不合法 → 把错误回灌重试」写成一条明确链路。
- **命中 C6**：类型即文档，IR schema 演进时编译期就能发现问题。
- **弱项**：可观测与评测生态不如 LangGraph / Agents SDK 成熟；RAG 需要自己接（但我们的检索
  本来就放在 Rust 侧，反而无损失）。
- **适合**：把它当作「带类型契约的工具循环」用，而不是当作平台。

### 4.2 OpenAI Agents SDK —— 最省事的工具循环与 tracing

- **命中 C2/C4/C5**：轻量、无 SaaS 依赖、工具调用与 handoff 是一等公民，tracing 开箱，
  调试「为什么它选了那个工具」很直观。
- **命中 C1**：支持结构化输出（schema 约束），可以强制产出 IR。
- **弱项**：如果你需要跨进程的持久状态机，它不提供。
- **适合**：想让第一版尽快跑通、且愿意接受 OpenAI 生态心智的情况（模型侧仍可换 provider）。

### 4.3 LangGraph —— 流程一旦复杂，它的价值才出现

- **强项**：显式状态机 + 检查点 + 人工介入节点，天然表达「生成 IR → 编译失败 → 回灌 → 再次失败 →
  反问用户」这类带状态的分支；可断点续跑，便于把一次问答做成可审计的执行记录。
- **代价**：概念面更大（State / Node / Edge / Checkpointer），团队要先付学习成本；
  它容易把业务逻辑吸进图里，与本项目「编译语义留在 Rust」的纪律有张力（**纪律要靠人守**）。
- **判断**：**第一版不要上**。等到出现「多轮澄清 + 结果确认 + 审批 + 长任务」再迁移，
  届时你已经有清晰的节点划分，迁移成本反而低。

### 4.4 DSPy —— 不是 harness，是「把准确率刷上去」的优化器

- 它解决的是**用什么提示/少样本/模块组合**（signature、module、optimizer），而不是「怎么跑工具循环」。
- 与本项目极契合的一点：我们有 20 题标准集和「≥80% 一次过」的验收指标，正好是可优化的目标函数；
  DSPy 可以把手工调提示变成「用评测集自动搜」。
- **但它不能替代护栏**：IR 校验、EXPLAIN 预检、行列硬限仍然要自己写。
- **建议**：P3 后半段再引入，作为准确率调优手段；不要在第一版就压上来。

### 4.5 Haystack / LlamaIndex —— 检索很强，但我们的检索不在 Python 侧

- 二者的核心优势是索引与检索编排。而本项目已定：grounding 检索 API 在 **Rust 侧**（先 FTS）。
- 因此它们最强的那部分用不上；如果仅为了用一个 Agent 抽象而引入，性价比低。
- **例外**：当语料规模大到需要多路召回 + 重排，且决定把检索搬到 Python 时，再重新评估。

### 4.6 多智能体（CrewAI / AutoGen）—— 与本任务不匹配

- 问数是**一条主链路 + 少量分支**，不是多角色协商。多智能体会显著增加不确定性、token 成本
  和调试难度，而收益（角色分工）在这个任务上几乎为零。
- **结论：不采用**。

### 4.7 低代码平台（Dify / Coze / n8n）—— 原型可以，核心链路不行

- 优点：搭 demo 极快，非工程同学也能拖。
- 放不进核心链路的原因：
  1. **C1/C2**：难以强制「只产出 IR」并禁止它自行拼 SQL；
  2. **C3**：难以把「只读已发布版本」做成不可绕过的约束；
  3. **C5**：私有化与版本可控性参差；
  4. 配置即代码，**难以进 git、难以 code review、难以做回归评测**。
- **结论**：可以做内部演示，不要做产品主链路。

### 4.8 自研薄循环 —— 值得认真考虑的基线

链路本身很短：`检索 → 生成 IR → 校验 → 编译 → （失败回灌）→ 执行 → 解释`。
用官方 SDK + JSON Schema 校验 + 显式重试上限，约 200 行即可，好处是：

- 没有任何框架升级/弃用风险；
- 每一行都可测，评测集可以直接打到函数级；
- 与 C1–C6 全部对齐。

代价是要自己写 trace 与 eval（可用 OpenTelemetry + 简单 JSONL 记录起步）。
**建议**：把自研薄循环当作基线实现（baseline），再决定是否需要框架带来的额外能力；
如果一开始就选框架，也要保证「框架只做编排」这条纪律。

### 4.9 DeepSeek Harness（DSH）—— 架构最贴，成熟度最险

> 事实来源：`github.com/deepseek-ai/deepseek-harness`（MIT、TypeScript、2026-08-13 创建，
> 撰写本文时仍在高频迭代）、官方 `docs/architecture.md`、官网 `deepseek.com/harness`。

**它是什么**

DeepSeek 官方的开源 **agent harness**（不是模型，也不是低代码平台）。
口号是 *Everything is a Plugin*，底层是 [Cordis](https://github.com/cordiverse/cordis)：
插件向共享 context 贡献服务、类型化事件与**可回滚副作用**。
关键在于——**模型适配器、工具注册表、会话日志、乃至 agent loop 本身都是插件**，没有需要打补丁的
特权内核。这与我们「harness 只做编排、编译语义留在 Rust」的纪律天然同构：
我们不是去改它的内核，而是**在旁边挂一个插件**。

**集成面（这点很关键）**

它不是「又一个自带 UI 的 App」，而是按 profile 组合的运行时：

| Profile | 形态 | 对我们的意义 |
|---|---|---|
| `web` | 浏览器应用 | **不用**——我们有自己的前端 |
| `headless` | 一次性运行、无服务器 | 批处理评测、脚本化回归 |
| **`sdk`** | **SDK JSON-RPC 服务器** | **主要集成面**：起本地进程，我们的服务当客户端 |
| `sdk-minimal` | 单一 bundle 的显式 SDK 树 | 想裁剪依赖面时用 |
| `acp` | 自动化专用 ACP 服务器 | 与外部自动化编排对接 |

并且**有 Python SDK**：其 wheel 会把 `dsh` CLI 作为运行时打包，默认以 `dsh --profile sdk`
启动一个显式 Harness home 的进程。也就是说——**我们的 P3 服务可以继续是 Python（FastAPI），
把循环委托给本地 dsh 进程**，不必把 agent 层改写成 Node。

**逐条对照我们的硬约束**

| 约束 | DSH 的表现 |
|---|---|
| C1 LLM 不直出 SQL | **需实测**：`core/system-prompt` 负责 prompt-section 与 tool-schema 组装，但「最终回答能否被 JSON Schema 强约束」我没有验证到 ⇒ 列为**准入必测项** |
| C2 编译语义只在 Rust | **契合**：工具即插件，我们挂的工具只调 Rust 的 REST，不重写任何语义 |
| C3 只读已发布版本 | **可控**：把 `/released` 固化进我们自己的工具实现，插件侧绕不过去 |
| C4 重试上限 / 行列硬限 | **契合**：`core/tools` 自带**受守卫的执行管线**，base bundle 含 sandbox 与审批策略 |
| C5 私有化 | **契合**：MIT、纯本地进程、模型适配器可替换（BYOK），无 SaaS 控制面依赖 |
| C6 可评测 / 可追溯 | **契合且是亮点**：`core/session` 是 **append-only 的 SessionEvent 日志**，天然可重放；「回答附依据、可展开 SQL」几乎不用自己造轮子 |

**风险（按严重度）**

1. **成熟度——唯一但很重的减分项**。2026-08-13 创建，README 用大写明确写着
   *THERE WILL BE COMPATIBILITY-BREAKING CHANGES*，且标注 developer preview。
   把 to-B 建模平台的**核心问数链路**押在一个月龄的 pre-1.0 运行时上，需要有承担升级/返工的预算；
   `SAFETY.md` 也建议先行阅读。
2. **运行时栈变厚**。本体是 Node/TS；即便用 Python SDK，wheel 里也打包了 dsh CLI runtime——
   部署面从「Rust 单二进制 + 可选 Python」变成「还要带 Node 运行时 + 插件树」。
   对 on-prem 交付（依赖审计、离线镜像）这是实打实的成本。
3. **Cordis 学习曲线**。官方架构文档开篇即「assumes you know Cordis」，背后是一篇 arXiv 论文；
   生态小、文档新，深度定制（例如替换 agent loop）门槛不低。
4. **自带 UI 与我们的 UI 重叠**：只走 `headless` / `sdk` profile，别把 `web` 引入产品。

**判断**

- 架构契合度上是**所有候选里最高的**：插件化 + append-only 会话日志 + guarded tool pipeline，
  几乎是照着我们的约束长的，且**不违反任何一条红线**。
- 但它同时是**最年轻**的。所以结论不是「用」或「不用」，而是**怎么用**：
  **不作为 P3 第一版的默认依赖，而是并行评估的头号候选**（见 §5 双轨验证）。

## 5. 推荐方案

**分两步走，避免一次性押注：**

| 阶段 | 方案 | 说明 |
|---|---|---|
| P3 第一版 | **Pydantic AI**（或 OpenAI Agents SDK）+ 自研评测脚本 | 只做编排；IR 校验、编译、执行全在 Rust |
| P3 并行评估 | **DSH**（`dsh --profile sdk` / `headless`）跑同一套工具与评测集 | 满足准入条件再考虑替换第一版 |
| P3 调优期 | 叠加 **DSPy** 做 NL→IR 优化 + 扩充评测集 | 用数据提升一次通过率，而不是堆提示词 |
| 触发式升级 | 出现多轮澄清 / 审批 / 断点续跑 → **LangGraph** 或 DSH | 到那时节点划分已清晰，迁移成本低 |

### 5.1 双轨验证：让 DSH 用数据说话，而不是用印象

DSH 的架构契合度明显最高，但成熟度风险也最高。所以不要靠争论决定，靠一次**受控对比**：

1. **先把耦合面隔开**：在 Python 侧定义一个极薄的 `AgentRuntime` 接口
   （`ask(question) -> {ir, sql, rows, evidence, trace}`），第一版用 Pydantic AI 实现，
   DSH 作为第二个实现。**业务逻辑一律不写进 harness**，这样换 harness 的代价被压到最小。
2. **工具集只做一份**：`model_search` / `compile_ir` / `execute` 全部以 REST 暴露在 Rust 侧，
   两边都调同一批接口（DSH 侧是薄插件，Python 侧是函数工具）。
3. **同一套评测集**：20 题标准集 + 幻觉 SQL 一票否决，两条链路跑同一份题，
   记录**一次通过率、平均步数、p95 延迟、token 成本、失败归因**。
4. **准入必测项**（不通过就不进入下一步）：
   - 能否用 JSON Schema 强制产出 IR（C1）；
   - 会话日志能否完整重放出「提问→命中 artifact→IR→编译诊断→SQL→行数」（C6）；
   - 工具执行管线能否落实重试上限与行列硬限（C4）；
   - 离线环境下 `dsh --profile sdk` 能否正常起停（C5）。
5. **决策规则**：
   - DSH 在**一次通过率或可追溯性**上明显更好，且团队愿意承担 pre-1.0 的升级成本 → 换 DSH；
   - 两边打平 → **留第一版**（成熟度优先）；
   - 结果记录进 `docs/dev-plan/changelog.md`，作为后续复评依据。

选 Pydantic AI 还是 Agents SDK 的判据：

- 团队更信「类型与契约」、IR schema 会频繁演进 → **Pydantic AI**；
- 团队更想少写代码、要现成 tracing、能接受生态绑定 → **OpenAI Agents SDK**。

无论选哪个，**四条红线不变**：

1. LLM 永不直出 SQL（只产出 IR）；
2. 编译/校验语义只存在于 Rust；
3. 只读已发布版本（`/released`），不读工作区；
4. 重试有上限，歧义必反问。

## 6. 与现有设计的衔接（落地时要补的东西）

- **Rust 侧**（`query.rs` / `existence.rs` / `release.rs`）：
  - IR 的 JSON Schema 需要先行，成为前后端与 Agent 的共同契约；
  - 暴露 `/api/repos/{id}/released` + IR 编译/执行接口，Agent 只走这些口子；
  - grounding 检索 API（FTS 起步）。
- **Python 侧**：
  - FastAPI 薄服务；harness 只做编排；
  - 预留 **`AgentRuntime` 薄接口**（§5.1），让 harness 可替换；DSH 走 `dsh --profile sdk`
    本地进程 + JSON-RPC，Python 侧当客户端，不必改写成 Node；
  - 每步记录 trace（提问、命中 artifact、IR、编译诊断、SQL、行数），直接支撑 20 题评测；
  - 会话与提问历史。
- **评测**：
  - 20 题标准集固化为回归测试；「拒答/反问」计入通过，**幻觉 SQL 一票否决**。

## 7. DSH 仍需核实的点

本文关于 DSH 的事实来自其仓库 README 与 `docs/architecture.md`，以下细节**尚未验证**，
建议在双轨评估（§5.1）前先补齐：

1. **结构化输出**：能否对最终产出施加 JSON Schema 约束（IR 契约的硬前提）。
2. **插件 API 稳定性**：第三方工具插件的公开接口是否已稳定，文档是否够用。
3. **Python SDK 的实际体感**：打包 wheel 的体积、启动 `dsh --profile sdk` 的开销、
   以及是否需要联网拉取 bundle。
4. **许可证与依赖审计**：MIT 本体没问题，但要确认插件树里第三方依赖的许可与体积。
5. **版本节奏**：developer preview 期间的破坏性变更频率，以及是否已有 release 分支可钉版本。

> 注：以上不确定性正是「不作为第一版默认依赖」的理由，而不是否定它的理由。

## 8. 一页速查

```
要契约、要类型        → Pydantic AI
要少写代码、要 trace  → OpenAI Agents SDK
要状态机、要审批      → LangGraph（第二阶段）
```
